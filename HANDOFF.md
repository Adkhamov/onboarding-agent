# MoonAI Onboarding-Agent — техническая спецификация для фронтенд-разработчика

> Прототип → продакшн. Один файл, который описывает **всю** бизнес-логику текущего
> прототипа: экраны, промпты (дословно), схему данных, контракт бэкенда,
> дизайн-токены — и отдельно то, что в прототипе является заглушкой и должно
> стать настоящей продакшн-логикой.

- Живой прототип: https://web-production-b4ffd1.up.railway.app (пароль указывается отдельно, см. переменную `SITE_PASSWORD`)
- Репозиторий: https://github.com/Adkhamov/onboarding-agent
- Стек прототипа: **один файл `index.html`** (весь UI и вся логика, ванильный JS, без фреймворка и без сборки) + **`server.js`** (Node.js без зависимостей, кроме `unpdf`) как тонкий бэкенд/прокси.
- Итоговый артефакт, который производит мастер: **системный промпт** (`buildPrompt()`) + **JSON-схема двух функций** (`buildTools()`), которые ИИ-агент вызывает в диалоге.

---

## 0. Что именно нужно перенести в продакшн

Это **не** просто форма. Мастер — это конвейер:

```
Ответы клиента (16 экранов)
        │
        ├─► «магия» (LLM) обогащает и адаптирует поля под нишу/данные источников
        │
        ▼
   state.data (единый объект состояния)
        │
        ├─► buildPrompt(state.data)  →  системный промпт (строка)
        └─► buildTools(state.data)   →  JSON-схема save_lead() и escalate_to_human()
```

Задача — перенести **всю** эту логику (шаги, дефолты, промпты, правила слияния
ИИ-подсказок с ручным вводом, генерацию `buildPrompt`/`buildTools`) на реальный
стек продукта, заменив прототипные заглушки (см. раздел 11) на настоящую
инфраструктуру: базу данных, реальную аутентификацию, реальную доставку
`save_lead`/`escalate_to_human` в CRM, и т.д.

## 1. Архитектура: прототип vs продакшн

| Компонент | В прототипе | Что должно быть в проде |
|---|---|---|
| Frontend | 1 файл `index.html`, ванильный JS, глобальный объект `state` | React/Vue-компоненты, состояние в сторе (Redux/Zustand/Pinia), пер-пользовательская сессия |
| Хранение состояния мастера | Только в памяти вкладки браузера, ничего не персистится, пока не нажали «Сохранить агента» | Автосохранение черновика в БД по мере заполнения (как минимум — на каждый переход между шагами) |
| «Мои агенты» | `localStorage`, JSON-экспорт/импорт вручную | Таблица `agents` в БД, привязанная к аккаунту/workspace |
| Аутентификация | Один общий пароль на всё приложение (`SITE_PASSWORD`) | Настоящая аутентификация платформы (пользователь/воркспейс) |
| API-ключи LLM | Общие ключи на сервере в env, шара на всех | Ключи уровня платформы/тарифа, привязка usage к конкретному аккаунту |
| Usage-учёт | Один файл `usage.json` на диске, глобальный счётчик | Таблица usage в БД, разбивка по аккаунту/агенту |
| `save_lead` / `escalate_to_human` | Демо: просто рисуют карточку в чате, ничего никуда не отправляют по-настоящему (кроме тестового Telegram) | Реальный вызов вебхука/CRM API, запись лида в БД, реальная маршрутизация эскалации |
| Голос → текст, PDF → текст, парсинг сайта/2ГИС/Instagram | Через простые серверные прокси-эндпоинты | То же самое, но с квотами/лимитами на аккаунт, очередями, ретраями с бэкоффом |

## 2. Полный флоу — 17 экранов по порядку

Экраны идут строго **линейно вперёд** (см. раздел 7.1), назад — свободно.

| # | `id` шага | Заголовок | Что вводит пользователь → куда пишется в `state.data` | Особая механика |
|---|---|---|---|---|
| 0 | `welcome` | Заставка | — | Кнопка «Поехали» → `go(1)` |
| 1 | `template` | Ниша | `niche`, `nicheDetail` (текст + `<datalist>` на 30 вариантов) | На «Далее» — `kickoffEarlyMagic()`, см. 4.1 |
| 2 | `sources` | Ссылки | `state.sources[]` — любые ссылки, автоопределение типа | См. 2.1 |
| 3 | `materials` | Файлы/текст | `state.sources[]` (type `file`) — PDF/TXT/MD/CSV, вставка текста | На «Далее» — запуск `startBackgroundParse()`, см. 4.2 |
| 4 | `channels` | Каналы | `channels[]` — whatsapp/instagram/telegram/site (мультивыбор) | Влияет на текст в промпте (видимость номера) |
| 5 | `integrations` | Интеграции | `integrations[]`, `integrationRequests[]` | Каталог фиксированных карточек, см. 2.2 |
| 6 | `basics` | О компании | `companyName`, `about`, `agentName`, `avatar`, `langs`, `geo`, `hours`, `currency`, `timezone` | Большинство полей — авто-заполняются «магией», если пустые |
| 7 | `prices` | Цены | `pricing` | Отдельный шаг специально из-за важности цен |
| 8 | `goal` | Цель (КЭВ) | `goal` | Карточки-варианты + свой текст, редактируемо двойным кликом |
| 9 | `style` | Стиль общения | `style`, `styleP` (эмодзи/обращение/теги) | Двухшаговая генерация вариантов через ИИ, см. 2.3 |
| 10 | `restrictions` | Запреты | `restrictions[]` (`{text, on}`) | Тумблеры, двойной клик — редактировать текст |
| 11 | `flow` | Сценарий диалога | `stages[]` (`{icon,title,desc,msg}`) | Визуальный флоучарт, генерация под нишу |
| 12 | `faq_q` | FAQ — вопросы | `faq[]` (`{q,a}`), заполняются `q` | `part:[1,2]` — визуальный под-степпер |
| 13 | `faq_a` | FAQ — ответы | `faq[].a` | Ручной ввод / голос (Whisper) / автогенерация; `part:[2,2]` |
| 14 | `handoff` | Передача менеджеру | `escalate.triggers[]`, `unknown`, `escalate.notify[]`, `telegram`, `escalate.sendFields[]` | 4 подраздела в одном экране, см. 2.4 |
| 15 | `data` | Данные для заявки | `dataFields[]` (`{text,on}`) | Питает `buildLeadParams()` — см. раздел 6 |
| 16 | `finish` | Готово | — | Сначала «эффект сборки» (5–10 сек), потом промпт/функции/чат, см. 2.5 |

### 2.1 Источники — правила нормализации ссылки

Функция `normalize(raw)` (index.html):
1. Если начинается с `@` → это Instagram-ник → `instagram.com/<ник>`.
2. Иначе: убрать `http(s)://`, `www.`, пробелы, обрезать хвостовой `/`.
3. Домен обязан пройти `/^[a-z0-9а-я.-]+\.[a-zа-я]{2,}$/i`, иначе ошибка.
4. Тип определяется по `detectType()`:
   - содержит `2gis` → `2gis`
   - `instagram.com` или начинается с `@` → `instagram`
   - `wa.me` / `whatsapp` / `t.me` / `telegram.me` / `tg://` → `link` (просто сохраняем как контакт, не парсим)
   - иначе → `website`

### 2.2 Каталог интеграций (фиксированный список)

`INTEGRATIONS` в коде — 9 карточек: AmoCRM, Битрикс24, Google Sheets, Google
Calendar, Проверка Kaspi-чеков, Kaspi Pay, Custom Integration (все — кнопка
«Подключить»/«Отключить», по сути toggle) и Jivo, U-ON (кнопка «Оставить
заявку» — тип `request`, не toggle). В проде это должно стать **настоящим
OAuth/API-key подключением**, а не просто отметкой в форме — сейчас это
**выбор для сценария**, реальная интеграция не происходит.

### 2.3 Стиль — двухфазный подбор тона

1. Пользователь отмечает: эмодзи (нет/иногда/да + набор конкретных эмодзи),
   обращение (ты/вы), теги тона (коротко, тепло, по-деловому, с юмором,
   маленькими буквами, без канцелярита, энергично).
2. `stylePrefs(styleP)` собирает это в текстовое summary — это и есть
   `state.data.style` **по умолчанию**, ещё до генерации примеров.
3. По кнопке «Показать примеры общения» — отдельный ИИ-вызов (см. промпт в
   4.4), возвращает **ровно 2** варианта первого сообщения. Пользователь
   выбирает один (тогда `style = summary + ". Пример: «…»"`) или жмёт «Ещё
   варианты» / пишет комментарий и перегенерирует.
4. Альтернатива — свободный текст в поле «опишите своими словами».

### 2.4 Передача менеджеру — 4 подраздела на одном экране

1. **Когда передавать** — тумблеры-триггеры (`escalate.triggers`, дефолт из
   `DEFAULTS.escalate_triggers`).
2. **Как отвечает при передаче** — варианты из `unknown_options` (тот же
   список, что и «если не знает ответа» — они логически совпадают).
3. **Куда уведомление** — Telegram (реально работает, см. раздел 9.4) или
   CRM/webhook (заглушка «скоро»).
4. **Что отправить менеджеру** — чипы `escalate.sendFields`.

### 2.5 Финал — «эффект сборки»

`renderFinish()` при первом входе на шаг НЕ показывает результат сразу:
показывает 5 этапов-псевдопрогресса (`FINISH_STAGES`, ~1.1–1.6 сек каждый,
итого ~7–10 сек) со случайной подсказкой снизу (`FINISH_QUOTES`), и только
потом (`state._finishReady = true`) рендерит реальный контент — вкладки
«Промпт» / «Функции» / «Тест-чат» — с конфетти. При повторном возврате на
шаг анимация не повторяется. Это чисто UX-приём (ощущение «работы»), реальных
операций во время этой паузы не происходит — **можно и нужно** в проде
заменить на реальную асинхронную операцию (сохранение агента в БД,
регистрация функций и т.п.), если она появится.

## 3. Модель данных — `state.data` (полная схема)

```ts
interface AgentDraft {
  // Ниша
  niche: string;
  nicheDetail: string;

  // Каналы и интеграции
  channels: ("whatsapp"|"instagram"|"telegram"|"site")[];
  integrations: string[];           // id из INTEGRATIONS, коннект-тип
  integrationRequests: string[];    // id из INTEGRATIONS, request-тип ("оставить заявку")

  // О компании
  companyName: string;
  sphere: string;                   // используется только как fallback для about
  about: string;
  agentName: string;
  avatar: string;                   // один эмодзи
  langs: string;                    // "Русский, казахский"
  geo: string;
  hours: string;
  currency: string;
  timezone: string;
  pricing: string;

  // Цель и сценарий
  goal: string;
  stages: { icon: string; title: string; desc: string; msg: string }[];

  // Стиль
  style: string;                    // финальная текстовая формулировка для промпта
  styleP: {
    emoji: "no"|"some"|"yes";
    emojiSet: string[];             // выбранные эмодзи-символы
    address: "ты"|"вы";
    tags: string[];                 // "коротко","тепло", ...
  };

  // Запреты
  restrictions: { text: string; on: boolean }[];

  // FAQ
  faq: { q: string; a: string }[];

  // Передача менеджеру
  unknown: string;                  // выбранный вариант ответа "не знаю"
  escalate: {
    triggers: { text: string; on: boolean }[];
    notify: ("telegram"|"crm")[];
    sendFields: { text: string; on: boolean }[];
  };
  telegram: { chat_id: number|null; name: string };

  // Данные для заявки
  dataFields: { text: string; on: boolean }[];

  // Тихие дефолты (без отдельного экрана в текущей версии, см. 11)
  disclose: "soft"|"open"|"hide";
  stoptopics: string;
}
```

Плюс на уровне `state` (не `state.data`):
- `state.sources[]` — источники (`{id, type, clean, full, text?}`), включая `type:"file"`.
- `state.suggestions` — последний результат «магии» (см. раздел 4), той же формы, что `DEFAULTS`.
- `state.generated: boolean` — «магия» хотя бы раз отработала.
- `state.parsedContext: string` — склеенный текстовый контекст из всех источников (передаётся в LLM).
- `maxStep` (модульная переменная) — максимально достигнутый индекс шага, для линейной навигации.

## 4. «Магия»: как ИИ обогащает форму

Все ИИ-вызовы идут через единый прокси `POST /api/llm` (см. раздел 8) —
ключи Claude/OpenAI **не покидают сервер**.

### 4.1 Когда вызывается `generateSuggestions()`

Это главная функция обогащения — вызывается в **трёх** случаях (всегда одна и та же функция, разный контекст):

1. **Сразу после ввода ниши**, до всяких источников — `kickoffEarlyMagic()`
   на «Далее» с шага `template`. Контекст — только ниша + специализация (без
   данных источников). Это «нулевая фаза» адаптации.
2. **После фонового парсинга источников** — `startBackgroundParse()`
   (см. 4.2) вызывает `generateSuggestions(state.parsedContext)` — теперь с
   реальными данными сайта/2ГИС/Instagram/файлов. Это **вторая, уточняющая
   фаза** — перезаписывает результат первой фазы более точными данными.
3. **Вручную** — кнопка «✨ Заполнить магией из источников» на шагах О
   компании / Цены / Цель / Стиль / Запреты (`wireMagic()`).

### 4.2 Фоновый парсинг источников — `startBackgroundParse()`

Запускается на «Далее» с шага `materials`, **не блокирует** переход —
пользователь идёт дальше (Каналы → Интеграции → О компании...), а сбор данных
идёт в фоне. Прогресс показывается **persistent-баннером** под прогресс-баром
(виден на любом шаге, не только на шаге источников):

```
Собираю данные из источников… 2/3
     ↓ (после сбора всех источников)
Анализирую через ИИ и заполняю поля…
     ↓
Данные собраны — поля предзаполнены ✅   (баннер держится 4.5 сек и скрывается)
```

Псевдокод:
```js
async function startBackgroundParse() {
  if (state.parsing || state.generated) return;
  for (const src of state.sources) {
    // file → берём текст как есть
    // link (wa.me/t.me) → не парсим, просто помечаем как контакт
    // website/2gis/instagram → POST /api/parse
  }
  state.parsedContext = buildContext(results);          // склейка в один текст
  if (hasKey) await generateSuggestions(state.parsedContext);
  state.generated = true;
  // если пользователь сейчас на шаге, зависящем от данных, и не печатает — перерисовать
}
```

### 4.3 Главный промпт обогащения — `GEN_SYS` (дословно)

Это единственный промпт, который видит **все** собранные данные и на выходе
даёт JSON, который потом используется для предзаполнения полей и как
источник вариантов (`state.suggestions`) для карточек-выборов на следующих
шагах.

**System prompt:**
```
Ты помогаешь настроить ИИ-агента продаж/поддержки для бизнеса. По данным о компании верни СТРОГО валидный JSON без markdown, ровно по схеме:
{"company_name":"","sphere":"","about":"","address":"","working_hours":"","prices":"","agent_names":["","",""],"goals":["","","",""],"styles":[{"title":"","example":""},{"title":"","example":""},{"title":"","example":""}],"restrictions":["","","","","",""],"faq":[{"q":"","a":""}],"unknown_options":["","",""],"data_fields":["","","",""],"languages":"","stop_topics":""}
Правила:
- company_name, about, sphere, address, working_hours, prices — ТОЛЬКО из предоставленных данных; если нет данных — оставь "".
- company_name — это РЕАЛЬНОЕ название бизнеса. НЕ бери название каталога/справочника/агрегатора и не бери заголовок вкладки браузера (например «2ГИС», «Otzyv», «Instagram»). Если названия в источниках расходятся — выбери то, что похоже на официальное имя компании. Если уверенности нет — оставь "".
- prices — самое важное поле для клиента. Внимательно вычитай данные и найди КОНКРЕТНЫЕ цифры (цены, тарифы, «от X ₸/₽/$», прайс-лист), даже если они упомянуты вскользь или в разных источниках. Приведи их списком с валютой. Если цифр нет вообще — оставь "", не обобщай и не выдумывай.
- agent_names: 3 коротких имени-варианта для ассистента.
- goals: 4 реалистичных целевых действия (КЭВ) для этой сферы и специализации.
- styles: тон/voice — второе по важности после цен. Дай 3 РАЗНЫХ тона, реалистичных именно для этой ниши и специализации (например, мед. клиника ≠ барбершоп ≠ турагентство по звучанию). Пиши по-человечески, эмодзи — уместные и редкие (не в каждом сообщении). Один из вариантов — casual маленькими буквами. example — живое первое сообщение агента без канцелярита, отражающее подачу именно этого бизнеса.
- restrictions: 5-6 ТОЛЬКО рабочих запретов (нельзя называть точную цену без уточнения; обещать результат/сроки; сравнивать с конкурентами; давать мед/юр советы; выдумывать факты). Без банальностей вроде «быть вежливым».
- faq: 8-10 реальных частых вопросов клиентов сферы с короткими ответами (используй факты из данных, где есть).
- unknown_options: 3 варианта поведения, если агент не знает ответа.
- data_fields: 4-6 полей, которые агенту стоит собрать у клиента.
- languages: вероятные языки общения. stop_topics: темы, которых агент избегает.
Только JSON, на русском.
```

**User message** (шаблон):
```
[Ниша бизнеса: {niche}. Специализация: {nicheDetail}.]

Данные о бизнесе:

{parsedContext ИЛИ "(данных мало, опирайся на нишу и общую логику)"}
```

Модель: `max_tokens=3000`, раздел usage-учёта — `"suggestions"`.

**Разбор ответа и слияние с состоянием** (важные детали для переноса!):
```js
// 1) Варианты для карточек-выборов — ВСЕГДА перезаписываются (с фоллбэком на DEFAULTS, если ИИ не ответил)
S.goals = arr(g.goals, DEFAULTS.goals);
S.styles = arr(g.styles, DEFAULTS.styles);
S.restrictions = arr(g.restrictions, DEFAULTS.restrictions);
S.faq = arr(g.faq, DEFAULTS.faq);
S.unknown_options = arr(g.unknown_options, DEFAULTS.unknown_options);
S.data_fields = arr(g.data_fields, DEFAULTS.data_fields);
S.languages = g.languages || DEFAULTS.languages;
S.stop_topics = g.stop_topics || DEFAULTS.stop_topics;

// 2) Прямые поля формы — ЗАПОЛНЯЮТСЯ ТОЛЬКО ЕСЛИ ПУСТЫ (не затирают ручной ввод пользователя!)
if (g.company_name && !D.companyName) D.companyName = g.company_name;
if ((g.about || g.sphere) && !D.about) D.about = g.about || g.sphere;
if (g.address && !D.geo) D.geo = g.address;
if (g.working_hours && !D.hours) D.hours = g.working_hours;
if (g.prices && !D.pricing) D.pricing = g.prices;

// 3) Имя агента — НЕ берётся у ИИ (см. раздел 11.6), берётся из фиксированного списка
if (!D.agentName) D.agentName = NAME_OPTIONS[0]; // NAME_OPTIONS = ["Аяна","Динара","Алия","Санжар","Мия"]

// 4) Язык/стоп-темы — перезаписываются БЕЗ условия (для них больше нет отдельного экрана ручного ввода)
if (S.languages) D.langs = S.languages;
if (S.stop_topics) D.stoptopics = S.stop_topics;
```

**Правило для продакшна:** «предзаполнение только если пусто» для
company/about/geo/hours/pricing — это то, что не даёт «магии» затирать то,
что пользователь уже вписал руками. Это должно сохраниться 1-в-1.

## 5. Итоговый промпт — `buildPrompt()`

Промпт собирается из фиксированных секций через разделитель:
```js
const B = (title, body) => body ? `\n\n────────────────────────\n## ${title}\n${body}` : "";
```
**Секция полностью пропускается, если тело пустое** — важно: пустых
заголовков в итоговом промпте быть не должно.

Порядок секций (дословный шаблон, `{...}` — подстановки):

```
Ты — [{agentName}, ]ассистент компании «{companyName}». Ты общаешься с клиентами в мессенджере и являешься первым контактом: помогаешь, отвечаешь на вопросы и мягко ведёшь клиента к целевому действию.

{about}
```

## 6. Функции (tools) — `buildTools()` / `buildLeadParams()`

**Это не просто документация внутри промпта — это буквально JSON-schema,
которая передаётся в Anthropic (`tools`/`input_schema`) и OpenAI
(`tools`/`function.parameters`) как контракт tool-calling** в тестовом чате
прототипа. В проде это должна быть та же схема, сгенерированная тем же
способом при сборке агента, и **сохранённая** как часть конфигурации агента
(а не пересчитываемая каждый раз на лету из сырого состояния формы — хотя
логика генерации должна остаться идентичной).

### 6.1 `save_lead` — параметры динамические, из шага «Данные»

```js
const CANON = [
  { key: "name",           match: /имя/i },
  { key: "phone",          match: /телефон/i },
  { key: "email",          match: /e-?mail|почта/i },
  { key: "request",        match: /услуг|запрос/i },
  { key: "preferred_time", match: /врем|дата/i },
];
```
Для каждого включённого (`on: true`) поля из `dataFields` ищем совпадение по
regex → если нашли, ключ в JSON-схеме — каноническое имя (`name`, `phone`,
...); если нет — `field_1`, `field_2`, ... **Описание (`description`) в схеме
— всегда оригинальный текст поля**, как его ввёл/отредактировал пользователь
(так что даже с generic-ключом `field_1` модель понимает, что там должно
быть). Если пользователь ничего не выбрал — фоллбэк `{name, phone}`
обязательными. К списку всегда молча добавляется необязательное поле
`notes` («Дополнительные детали из диалога»).

**`description` функции** генерируется динамически:
```
Вызывай, когда клиент подтвердил «{goal}» и собраны нужные данные. Передаёт заявку менеджеру[ и фиксирует в: {названия подключённых CRM-интеграций}].
```

### 6.2 `escalate_to_human` — параметры фиксированные, триггер динамический

Параметры всегда одни и те же: `reason` (string, обязат.), `summary` (string,
обязат.), `urgency` (`"low"|"medium"|"high"`, необязательно).

**`description`:**
```
Вызывай когда: {escalate.triggers, только on:true, через "; " ИЛИ дефолт "клиент просит человека, жалоба, вопрос вне знаний, или ты не уверен"}. Передаёт диалог живому менеджеру.
```

### 6.3 Куда уходит уведомление — `notifyChannels()`

```js
function notifyChannels() {
  const bits = [];
  if (D.telegram.chat_id && D.escalate.notify.includes("telegram")) bits.push("Telegram");
  const crmNames = D.integrations.map(id => INTEGRATIONS.find(i => i.id === id)?.name).filter(Boolean);
  if (crmNames.length) bits.push(crmNames.join(", "));
  return bits; // используется и в тексте buildPrompt(), и в UI-вкладке "Функции"
}
```

**Важно:** в прототипе и `save_lead`, и `escalate_to_human` уведомляют в один
и тот же список каналов (см. `notifyTelegram(tc)` в разделе 9.4) — то есть
если Telegram подключён на шаге «Передача менеджеру», уведомления приходят
**по обеим функциям**, не только по эскалации. Это осознанное решение,
сохранить в проде.

## 7. Навигация и state machine

### 7.1 Линейная навигация вперёд

```js
let maxStep = 0;
function go(n) {
  state.step = clamp(n, 0, STEPS.length - 1);
  if (state.step > maxStep) maxStep = state.step;
  render();
}
```
`go()` сам по себе **не ограничивает** прыжки вперёд (это нужно для
восстановления сохранённого агента — `applyAgent()` сразу переносит на
нужный шаг). Ограничение — на уровне **точек входа**:
- Кнопка «Далее» (`next()`) всегда идёт на `+1` — ограничение не нужно.
- Клик по пункту чек-листа в панели агента — **единственное** место, где
  теоретически можно прыгнуть вперёд, и там стоит явная проверка:
  `if (idx <= maxStep) { кликабельно } else { title="Откроется, когда дойдёте до этого шага"; cursor:default }`.

**В проде это правило нужно сохранить**, но проверку стоит перенести и на
роутинг (если шаги — отдельные URL) — прямой переход по URL на непройденный
шаг тоже должен блокироваться/редиректить на `maxStep`.

### 7.2 Панель «Ваш агент» — сила и растущий профиль

`STRENGTH` — **6 сгруппированных** пунктов (было 9 плоских, намеренно
сокращено — см. историю решений в разделе 11). Правило отбора: **пункт
существует только если что-то из него реально попадает в промпт или
функции**. Источники сами по себе не входят в промпт (входят только данные,
которые из них извлечены) — поэтому «Источники» не пункт чек-листа.

```js
const STRENGTH = [
  { key:"profile",  weight:20, label:"О компании",              test: companyName && about && langs },
  { key:"channels", weight:15, label:"Каналы и интеграции",      test: channels.length > 0 },
  { key:"goalflow", weight:20, label:"Цель и сценарий",          test: goal && stages.length > 0 },
  { key:"voice",    weight:15, label:"Стиль и запреты",          test: style && restrictions.length > 0 },
  { key:"support",  weight:20, label:"FAQ и передача менеджеру", test: faq.length > 0 && escalate.triggers.some(on) },
  { key:"data",     weight:10, label:"Данные для заявки",        test: dataFields.length > 0 },
]; // сумма весов = 100
```

Плюс **«растущий профиль»** (`renderFacts()`) — под чек-листом отдельным
рядом чипов показываются конкретные факты по мере заполнения: ниша,
количество источников, название компании, каналы, интеграции, языки, число
вопросов FAQ, число полей заявки. Обновляется на каждый `updateAgent()`.

### 7.3 Паттерн inline-редактирования (`editableText`)

Переиспользуемая функция для двойного клика → редактирование текста прямо в
карточке/чипе/тумблере (без модалок):

```js
function editableText(el, onSave) {
  el.addEventListener("dblclick", e => {
    e.stopPropagation();
    el.contentEditable = "true"; el.focus();
    // выделить весь текст
    const finish = () => { el.contentEditable = "false"; onSave(el.textContent.trim()); };
    el.addEventListener("blur", finish, { once: true });
    el.addEventListener("keydown", ev => { if (ev.key === "Enter") { ev.preventDefault(); el.blur(); } });
  });
}
```
Используется на: варианты Цели, варианты Стиля (заголовок и пример отдельно),
варианты «Если не знает», запреты, триггеры эскалации, чипы данных для
заявки, чипы «что отправить менеджеру». **Коммит происходит по потере
фокуса** (`blur`), Enter — просто вызывает `blur()` программно.

### 8.2 Модели и цены (для usage-подсчёта)

```js

// цена — $ за 1M токенов [input, output]
```

## 9. Интеграции с внешним миром

### 9.1 MoonAI-парсер (основной)

- База: `PARSER_BASE`, авторизация — заголовок `Authorization: <ключ>` **без**
  `Bearer` (с `Bearer` — 401, проверено).
- `POST /api/v1/parsers/general?url=` → `{html}` — сервер сам режет HTML→текст (`htmlToText()`, обрезка до 15 000 симв.).
- `POST /api/v1/parsers/2gis?url=` → `{company_name, company_category, company_address, branches_count, working_hours, phone_number}`.
- `POST /api/v1/parsers/instagram/profile?url=` → `{ig_username, ig_display_name, ig_bio, ig_bio_link, ig_followers_count, ig_recent_captions[]}`.
- **Ретраи**: Instagram — 3 попытки (анти-бот регулярно "флапает"), остальное — 2, с задержкой 1.5 сек и проверкой, что ответ реально содержит данные (не просто `200 OK` с пустым телом).

### 9.2 Собственный парсер 2ГИС (опционально, через `TWOGIS_API_KEY`)

Официальный `catalog.api.2gis.com/3.0/items/byid` — используется **вместо**
MoonAI-парсера, если ключ задан (иначе тихий fallback на MoonAI). Прямой
скрейпинг 2ГИС **не работает** — сайт редиректит нераспознанных ботов на
собственную анти-бот заглушку («museum» loader), это подтверждено на
практике при разработке прототипа.

### 9.3 Извлечение текста из PDF

Используется библиотека **`unpdf`** (современный pdf.js), **не**
`pdf-parse` — та библиотека регулярно падает с ошибкой `"Invalid number"` на
вполне обычных PDF (проверено на практике). При переносе — сохранить именно
`unpdf`.

### 9.4 Telegram-уведомления

⚠️ **Способ подключения в прототипе — временный хак, не переносить as-is**
(подробности — раздел 11.3): `/api/telegram/link` вызывает Telegram
`getUpdates` (long-polling API) и берёт **последний чат, который писал
боту** — то есть предполагается, что пользователь только что открыл бота и
нажал Start. Это работает для одного человека, тестирующего прототип, но
**не масштабируется** на многопользовательский продакшн (нет привязки к
конкретному аккаунту/сессии инициации).

Реальная отправка (`/api/telegram/send`, `notifyTelegram()`) работает
корректно и переносится как есть — по `chat_id` отправляется
HTML-форматированное сообщение с деталями вызова функции (какая функция,
какие параметры).

### 9.5 Транскрипция голоса

`MediaRecorder` (браузер) → `audio/webm` → base64 → `/api/transcribe` →
OpenAI Whisper (`whisper-1`, `language: "ru"`). Используется на шаге FAQ —
ответы можно надиктовать вместо печати.

## 10. Дизайн-система

Прототип использует токены и компонентный язык из
**github.com/howardat/moonai-ui** (индиго-акцент, Geist Variable/Geist Mono,
OKLCH-палитра, плоские hairline-карточки вместо мягких теней, статусы —
soft-tint). Ключевые решения:

- `--brand` (`#6A5EFD`) — **только** для логотипа/декоративных градиентов, не для интерактивных элементов.
- `--primary` (`#4F46E5`) — все интерактивные поверхности: кнопки, фокус, выбранные состояния, прогресс-бары.
- `--ring` (`#6366F1`) — именно для focus-ring (немного отличается от `--primary`).
- Радиусы: `sm=6 md=8 lg=10 xl=14 2xl=18` (шкала завязана на "чем крупнее поверхность — тем круглее угол").
- Тени → hairline-обводки: `--sh-1` = `0 0 0 1px oklch(...черный/8%)`, не цветная soft-shadow.
- Статус-цвета — пара: bare-токен (текст, AA-контраст) + `-mark`/`-tint`/`-border` (заливка/обводка, 15%/40% альфа).
- Полностью описано в исходном репозитории, `docs/DESIGN-SYSTEM.md`.

## 11. Технический долг прототипа — что НЕ переносить как есть

Это чек-лист для ревью перед продакшном.

1. **Глобальный `state`-объект на уровне модуля** — прототип не
   поддерживает нескольких одновременных пользователей на одном инстансе
   (в браузере это не проблема — у каждого пользователя своя вкладка, но
   архитектурно код написан как singleton). В React/Vue-переносе — это
   должно стать нормальным component state / store.

2. **Аутентификация одним общим паролем** (`SITE_PASSWORD`, один на всё
   приложение) — годится для демо, не для продукта. Нужна нормальная
   аутентификация с привязкой агента/usage к аккаунту.

3. **Telegram-подключение через `getUpdates`-хак** (раздел 9.4) — берёт
   «последнее сообщение боту», без привязки к сессии/аккаунту
   инициировавшего пользователя. В проде — либо webhook с state-параметром
   (deep-link `t.me/bot?start=<token>`), либо использовать
   Telegram-инфраструктуру, которая уже есть на платформе MoonAI, если она
   есть.

4. **`save_lead` / `escalate_to_human` — демо-заглушки.** Сейчас
   `pushToolResults()` в тестовом чате просто рисует "Заявка создана (демо).
   ID: LEAD-XXXX" — никуда реально не отправляет, кроме тестового Telegram.
   В проде вызов этих функций реальным агентом должен реально писать в
   БД/CRM/вебхук.

5. **"Мои агенты" в `localStorage`.** Экспорт/импорт JSON вручную. В проде —
   таблица в БД, привязанная к аккаунту, с версионированием (агент менялся
   со временем).

6. **Usage-учёт в одном JSON-файле на диске** (`DATA_DIR/usage.json`), общий
   на все запросы всех пользователей одновременно. Нужна таблица в БД с
   разбивкой по аккаунту/агенту.

7. **Имя агента раньше бралось у ИИ (`S.agent_names`), сейчас — только из
   фиксированного списка `NAME_OPTIONS`.** Это осознанное решение по
   фидбэку клиента ("не хочу, чтобы ИИ каждый раз выдумывал новое имя") —
   но в схеме `GEN_SYS` поле `agent_names` в JSON всё ещё запрашивается и
   генерируется, просто не используется для автозаполнения. При переносе —
   либо убрать поле из промпта (немного сэкономит токены), либо использовать
   его для чего-то другого (например, showcase вариантов).

8. **Мёртвый код: `renderRules()`.** Функция существует в файле (шаг «Язык
   и правила»), но **больше не зарегистрирована** в массиве `STEPS` — язык
   переехал на шаг «О компании», `disclose`/`stoptopics` стали тихими
   дефолтами. Функцию можно удалить при переносе.

9. **Шаблоны ниш "Поступление за рубеж" / "Турагентство" — не более чем
   toast-уведомление.** В `TEMPLATES`/`NICHE_LIST` эти ниши присутствуют как
   обычные строки для datalist, никакой отдельной логики/веток для них не
   реализовано (клиент собирался прислать отдельный сценарий позже — этого
   пока не произошло на момент написания документа).

10. **`editableText()` не всегда триггерится Enter-ом при программной
    симуляции** (проверено при QA) — реальные пользователи не затронуты
    (срабатывает по клику вне поля), но если в проде появятся E2E-тесты на
    эту фичу, тестировать через `blur`, а не через `keydown Enter`.

11. **Единый `PARSER_API_KEY`** — прототип полагается на партнёрский
    MoonAI-parser API как основной способ парсинга сайта/Instagram (2ГИС —
    опционально свой). В масштабе продакшна стоит оценить лимиты/SLA этого
    стороннего сервиса.

12. **Нет автотестов, нет TypeScript, нет сборки** — весь код — это один
    HTML-файл на ~1700 строк ванильного JS. Это осознанный выбор для
    быстрого прототипирования, **не** архитектурная рекомендация для
    продакшна.

## 12. Карта файлов прототипа

```
onboarding-agent/
├── index.html      — весь frontend: разметка, стили (:root-токены), вся JS-логика
├── server.js       — Node http-сервер: статика + /api/* прокси, без веб-фреймворка
├── package.json    — единственная реальная зависимость: "unpdf" (PDF → текст)
└── HANDOFF.md       — этот документ
```

Если переносите логику по частям — рекомендуемый порядок:
1. Схема данных (раздел 3) → типы/интерфейсы в новом стеке.
2. `buildPrompt()` + `buildTools()`/`buildLeadParams()` (разделы 5–6) — это
   чистые функции без побочных эффектов, переносятся почти дословно.
3. Промпты «магии» (раздел 4) — как есть, с прокси-эндпоинтом `/api/llm`.
4. Экраны мастера (раздел 2) — с учётом линейной навигации (7.1) и
   двухфазной адаптации (4.1–4.2).
5. Бэкенд-контракт (раздел 8) — реализовать на реальном бэкенде продукта,
   заменив заглушки по чек-листу раздела 11.
